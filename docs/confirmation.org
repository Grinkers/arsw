* Purpose

This file tracks confirmation of the audit findings in [[file:c.org][c.org]] and
[[file:python.org][python.org]].  The source reports are kept for human observation
and are NOT reordered or renamed.  Every finding here is investigated in the
order defined under [[*Order][Order]] below.

A confirmation marker records the outcome of each finding:

- =confirmed= :: the actionable core described in the report was reproduced or
  statically proven on the target tree.  The finding entry references a patch
  file under =docs/<ID>.patch= (for example =docs/C014.patch=) containing the
  minimal repro/test used to confirm it.
- =confirmed-no-issue= :: the reported core is not actually a defect on the
  target tree (for example upstream fixed it, or the reported behavior does not
  hold).  The entry records the evidence.
- =needs-more-attention= :: not yet investigated, blocked, or inconclusive.
  Every finding starts in this state until an attempt is logged.

Confirmed findings always link a patch file; =confirmed-no-issue= and
=needs-more-attention= entries carry an attempt log instead.

* Order

Findings are investigated strictly in the order below.  The goal is to surface
confirmed high-priority issues first to start triage, rather than spending all
effort confirming lower-severity or uncertain findings.  Order is:

1. Critical, then High, then Medium, then Low.
2. Within each severity, C findings before Python findings.
3. Within each severity/language block, ascending finding ID order.

This ordering is fixed; reports are not reordered to match it.

The complete ordered checklist (360 findings) follows.  Each item begins
unchecked; the checkbox records completion of the attempt (not the outcome).
The outcome is recorded by the marker in the finding's detail entry, and the
checkbox is ticked when that detail entry exists.

- [X] C014 [CRITICAL] A Python callback can re-entrantly finish an active backup
  :confirmed: [[file:C014.patch]]
  - CONFIRMED — use-after-free (SIGSEGV, exit 139).
  - Python 3.13.14, debug build, SQLite 3.53.4.
  - Repro: a custom VFS on the destination connection intercepts ~xWrite~
    during ~backup.step(-1)~.  On the second write, the Python callback
    calls ~backup.finish()~.  SQLite mutexes are recursive, so
    ~DBMUTEXES_ENSURE~ (sqlite3_mutex_try) in ~finish()~ succeeds on the
    same thread, and ~APSWBackup_close_internal~ calls
    ~sqlite3_backup_finish~ on the backup that ~sqlite3_backup_step~ is
    still operating on.  When ~xWrite~ returns, ~sqlite3_backup_step~
    resumes on freed state and crashes.
  - GDB backtrace: ~SIGSEGV at sqlite3_backup_step (sqlite3.c:85403)~
    ~sqlite3_mutex_leave(p->pDestDb->mutex)~ ← freed backup pointer;
    ~#1 APSWBackup_step src/backup.c:194~.
  - Cleaned up: temp databases removed.
